# JianghuSect — Element System & Edit Hub Design Review v0.3

**Status:** DESIGN ONLY — no Gemini prompt, implementation, source modification, GitHub push, or design freeze.

**Inspected build:** local `JianghuSect_main-1_v1.12.4_Small_Logic_Hotfix.zip` / extracted `JianghuSect_v1.10` source tree; this is **not** confirmation of the latest GitHub `main-1` head or any pending Gemini changes. Validate an exact commit/hash again before implementation.

## A. Source-audit findings (confirmed by reading code and executing a Node runtime catalog/spawn probe)

- `human_core.js` defines 23 affinity dimensions, comprising 8 elemental (`JD.CORE.affinityKeys.ELEMENT`) and 15 other crafting/martial affinities. Preserve all 23.
- The **8 base elements** are `FIRE`, `WATER_ICE`, `LIGHTNING`, `WIND`, `EARTH_METAL`, `WOOD_LIFE`, `YIN_SHADOW`, and `LIGHT_YANG`.
- `ASTRAL` and `BLOOD_DEMON` already exist in `SK.ELEM` and technique data. Treat these as **special disciplines/elements**, not default innate roots, unless separately approved.
- `NEUTRAL` is a no-element tag, not a ninth/tenth root.
- `h.root.grade` is already meaningful to cultivation and breakthroughs; do not replace it.
- `h.root.elements` is a legacy Thai five-element array generated by `human_core.js` with count `[5,4,2,1,1]` for `DEFECTIVE/MORTAL/SPIRIT/TRUE/HEAVENLY`. It should not automatically be treated as a new single-root/dual-root/triple-root system; the concepts contradict. Plan deterministic migration, legacy preservation and wording audit.
- Existing `h.affinities` should remain innate aptitude; `n.cult.tm` remains **per-technique mastery**; a new **per-element mastery** is a separate trainable state, preferably in `npc.ext.elementalSystem`.
- In the inspected runtime, `JD.TECH.techniques.length === 397` and `JD.TECH.mantras.length === 71`; these figures supersede older v0.2 draft counts of 285/61 for this particular baseline. Six techniques (five lacking a tag and one `METAL`) and 29 mantras have tags outside the chosen canonical 8+2+NEUTRAL set.
- Technique `element` tags use a mixture of canonical values and legacy tags (`WOOD`, `METAL`, `EARTH`, `WATER`, `ICE`, `YIN`, `YANG`, `LIGHT`, `BLOOD`, `CHAOS`, `FIVE_ELEMENTS`, etc.). A controlled alias/multi-element resolver is needed. Never silently map unknown tags to `NEUTRAL` in the new rules without audit; do not change existing combat behavior until tested.
- `CULT.SUBPREF` already consults elemental affinities for subpath scores; extend carefully rather than replacing NPC path-selection AI.
- The locked `js/human_core.js` must remain unchanged. `data/data_core.js` loads trait metadata consumed by Human Core; `C.extraTraits` is among supported trait registries, but automatic trait effects, creation timing, and extension root capacity still need integration tests.

### Edit Hub coverage audit

- `SECT.EDITOR.catalog()` builds a **hard-coded aggregation of selected registries** in `js/sect.js` (not all live runtime item types).
- Runtime catalog contains **1,104 entries**: provision 3, material 261, pill 8, crafted pill 120, equipment 158, manual 456, crystal 37, sub-manual 37, recipe scroll 14, organ 10.
- **Legendary weapons:** 11 definitions in `VC.LEGENDARY_WEAPONS` (7 weapon families). Each has a distinct `effects[].effectId`, and the battle code contains signature proc handling. **0/11 appear in the Edit Hub catalog**, because the catalog's equipment section enumerates equipment *recipes*, whereas these unique weapons are items registered into `JD.ITEMS.items` and `ECO.itemById` without repeatable recipes.
- The `EQUIPMENT` spawn dispatcher does support legendary IDs: runtime-probed `LEG_WPN_YITIAN_SWORD` created a valid `playerSpawned` item with `EFX_LEG_YITIAN_SEVER`. Its absence is a **discovery/UI catalog coverage defect**, not absence of the game asset or mint function.
- **Legendary arts:** 12 `JD.TECH.techniques` + 10 `JD.TECH.mantras`, and **22/22 are present** in the `TECH_MANUAL` catalog. Giving a manual is not equivalent to learning/equipping that technique or switching to its mantra.
- `UI.rEdit` lists **only the first 60** results via `catItems.slice(0, 60)`, without pagination. Searches `Legendary` and `ตำนาน` matched zero catalog items in the runtime test, because search only indexes name/ID/kind, not grade/rarity/effect/description. Search `LEG_` finds the 22 legendary arts. Category/tier filters can narrow results but not solve discovery systematically.
- Fishing additions: `FISHING.SPECIES` 10 fish, `FISHING.SPECIAL_ITEMS` 2 river-container/trash, and `FISHING.FISH_DISHES` 4 foods; **none appears** in Edit Hub's general catalog in the examined build. The two alchemy fish-recipes already appear.
- Edit Hub's character editor exposes neither root grade/composition nor elemental affinities, elemental mastery, learned technique management, active mantra selection, or a unified way to preview the full authored signature effects.
- Existing verification suites cover several systems but do not guarantee that **every live content registry is discoverable** in Edit Hub; add catalog-coverage regression checks.

## B. Proposed element architecture: reuse, not replacement

### B1. Single canonical 8 + 2 taxonomy

- Base roots / trainable elemental disciplines (8): `FIRE`, `WATER_ICE`, `LIGHTNING`, `WIND`, `EARTH_METAL`, `WOOD_LIFE`, `YIN_SHADOW`, `LIGHT_YANG`.
- Special technique disciplines (2): `ASTRAL`, `BLOOD_DEMON`.
- No-element: `NEUTRAL`/missing when explicitly authorized (never a root).
- Legacy alias resolver with a verified table (e.g. `WOOD -> WOOD_LIFE`, `WATER|ICE -> WATER_ICE`, `EARTH|METAL -> EARTH_METAL`, `YIN -> YIN_SHADOW`, `YANG|LIGHT -> LIGHT_YANG`) and explicit exceptions: `BLOOD`, `CHAOS`, `FIVE_ELEMENTS`, and unknown codes **require semantic review**, not blind aliasing.
- `FIVE_ELEMENTS` may be an explicit multi-element composite (weighted list) rather than an ordinary element.

### B2. Clearly separated dimensions

1. `h.root.grade` — existing quality grade and existing cultivation multipliers; preserve IDs, combat power and progression.
2. `npc.ext.elementalSystem.roots` — active innate elemental roots (default 1; 2 or 3 only with rare capacity traits), canonical element IDs and deterministic creation/migration. **Pending**: root grade labels/descriptions conflict with this policy and must be reconciled without changing numeric effects by accident.
3. `h.affinities[elementId]` — existing eight innate elemental aptitudes (among 23 total), *not* a new `rootAffinity` object.
4. `npc.ext.elementalSystem.mastery[elementId]` — trainable per-element mastery. This is separate from `n.cult.tm[techId]` (individual technique mastery).
5. `technique.element` / `mantra.element` / `subpath.elementTags` — canonical *metadata* and optional weights. Existing single-element techniques retain meaning and effects.
6. `ElementResolver` — one authoritative, pure calculation layer that consumes root composition, affinity, mastery and metadata and returns typed modifiers + explanation; stat/combat/cultivation pipelines consume the resolved result **once**.

### B3. Special elements

- `ASTRAL` and `BLOOD_DEMON` are not normal random roots and do not need additional core affinity stats.
- Special mastery may exist and grow from the relevant *unlocked, actually used* techniques or legitimate cultivation; zero until access is earned. Do not hand out a passive special-element damage boost merely because a NPC has a normal root.
- Access to special schools still follows the existing path, subpath, tier, library, unlock, cost, risk and forbidden-technique gates. Preserve existing unique visuals and authored effects.
- A later special attunement trait may be considered separately, but is **not approved** in this draft.

### B4. Relations and stacking

- Keep **two tables**: efficacy (`root -> skill.element`, match/oppose/neutral) and **directed** learning (`root -> element mastery learning speed`). Example to discuss: `WOOD_LIFE -> WATER_ICE` may help learning, without helping Water damage. No automatic symmetry.
- Multiple roots are a **choice of match** rather than additive full bonuses; for multi-element techniques evaluate per tagged element with explicit weights then normalize.
- Element-less content contributes zero bonus and zero penalty from elemental compatibility.
- Prefer a small cap and a central modifier budget; avoid stacking 5 unrelated multiplicative modifiers. Preserve all bespoke legendary weapon effects and spell behavior.
- Affinity influences innate learning and NPC tendencies; mastery influences elemental skill performance; per-technique mastery governs expertise in a specific technique. Ensure no double counting when an existing formula already uses affinity.
- A combat action with multiple hits/targets cannot grant duplicate mastery progression per hit/target; use once-per-action or once-per-real-training-event gain.

### B5. NPC / Save / UI

- NPC choice scoring adds **small** root relevance to existing preference, personality, interests, resource access, costs and risk calculations; do not turn NPCs into best-element robots or omniscient learners.
- Migration must be idempotent and deterministic; derive legacy active root from prior data + stable ID, retain raw five-element array, and avoid randomness at load. Do not overwrite `h.root.grade`. Never silently assign capacity traits to an old NPC without an approved migration policy.
- Character overview displays root grade/active roots/rare trait; a new mobile-friendly element tab keeps root, innate affinity, trained mastery, per-technique mastery and actual applied bonus breakdown distinct.
- Any Edit action must validate capacity vs trait, existing mastery ranges, path/skill constraints and cache invalidation; preview and undo should have the same side effects as commit or be pure/read-only.

## C. Proposed Edit Hub modernization

1. **Registry-driven Catalog:** normalized descriptors generated from source registries of materials, pills, recipes, items, VC unique legendary weapons, discovered manuals/mantras, fish/food/container types and future plugin providers. Deduplicate by `(kind,id)`; display source, rarity, tier, effect names and whether usable/spawnable.
2. **Provider + Action Adapters:** displayability is not the same as spawnability. Per type, define `list`, `validate`, `preview`, `create/transfer`, `teach`, `equip`, `adjust`, `undo` actions, allowing explicit disabled reasons for non-spawnable content. Do not directly mutate raw game state when gameplay service API exists.
3. **Legendary management:** show all 11 legendary weapons and all 22 legendary techniques/mantras; include a `Legendary` rarity filter and effect details; preserve unique world-instance enforcement in ordinary gameplay. Debug-spawned instances must be clearly flagged and remain excluded from illicit economy/donation/rarity accounting. The existing distinct `effectId` and `fxKind` must survive spawn/equip/save/load and not be genericized.
4. **Technique operations:** separate 'grant a manual', 'teach/unlock a technique', 'equip passive', 'set mantra', and 'adjust mastery'. Each must respect compatibility, learning prerequisites, ownership and editor/test permissions; neither receiving a manual nor joining the library implies direct learning.
5. **Pagination / mobile:** render 20–40 per page (or virtualized list), track total result count, support search by title, ID, alias, kind, rarity, effect ID/description, and filters for tier/rarity/source/spawn availability. Avoid a silent first-60 cutoff.
6. **Automatic coverage checks:** at startup/test enumerate public content registries and compare against Edit Hub descriptors. Every live entry is 'discoverable' or explicitly excluded with a reason. Add regression checks for 11/11 weapons, 22/22 legendary arts, 10 fish, 2 special river items and 4 dishes in the examined baseline, with counts re-evaluated on future versions.
7. **Safety:** developer items must never pay contribution points or duplicate authentic unique relics through normal ecology/market/quest channels; preview, rollback and save/load tests required.

## D. Proposed development sequencing (no action authorized yet)

- **Design 0:** Agree on 8+2 taxonomy, root-grade-vs-count migration, directed relation matrices, passive cap and the nature of special mastery.
- **Audit 1:** Re-read latest `main-1` source/commit; generate exact registry and call graph. Compare recent Gemini changes.
- **Patch A:** Fix Edit Hub catalog coverage, pagination, search and legendary/fishing support (a reusable platform task independent of elemental combat balancing).
- **Patch B:** Canonical element tag resolver and compatibility-only dry-run traces (no stat changes).
- **Patch C:** Active roots/trait capacity, stable migration, and mastered elements.
- **Patch D:** Connect real cultivation/combat effects and NPC decision-making with bounded bonuses and source breakdown.
- **Patch E:** Character UI/Edit integration and validation; run full regressions/multi-seed soak/Android browser performance.

## E. Design questions still undecided

1. For legacy root grades with names that imply five/two/one elements, is it acceptable to **keep their unchanged grade IDs and numeric multipliers but revise their descriptions** so root quantity is trait-controlled?
2. Should special mastery have the same 0–100 scale as ordinary mastery, but a different progression curve, or a separate special progression system?
3. Will general root match improve (a) cultivation speed and (b) elemental technique output by a small bounded amount, with no unconditional passive stat boost in first phase?
4. Should the editor grant **debug direct learning/equip** for legendary arts in addition to spawning manuals, guarded by eligibility and explicit debug provenance?
5. Should all runtime-registered items be shown in Edit Hub, including objects with no safe spawn action (visible read-only), or only items that can be spawned through validated adapters?
